# DACS Flutter construction mobile prototype study

## What is this workspace and how does it fit the ecosystem?

### Takeaway
The user confirmed through the coordinating chat that this Flutter workspace is an older prototype and is NOT IN USE. It is a worker material-request app using the old Firebase backend, not the native Attendance app and not the Web repository's dormant Android TWA; findings below are revival blockers or prototype defects, not active production incidents.

### Inferences
- Reuse the prototype as a procurement UX reference if useful. Reviving it requires an explicit backend/auth/identity migration and current procurement schema contract, not simply replacing a Firebase API key.
- Because it contains no job identifier, this app cannot by itself allocate requests to the correct construction job without a new contract; do not infer batchId means project or billing period.
- It provides no implementation of the Web money model and should remain outside accounting until deliberately designed; procurement progress must not become earned revenue/accomplishment.

### Gaps
- No live Firebase rules, data, indexes, users or Cloudinary preset policy were queried. Whether historical prototype data matters for migration remains unknown.
- Whether a future worker procurement surface should be a Web/PWA module, part of the supported Attendance app, or a separate revived Flutter app is a product decision.

## What are the concrete defects and integration risks if revived?

### Takeaway
The largest revival issues are backend separation, client-driven batch lifecycle, uncancelled request subscriptions and missing functional notification settings. Several source-level defects are definite; exposure through live authorization cannot be assessed because server rules are absent from the workspace and no live Firebase inspection was performed.

### Cited Findings
- **Confirmed subscription lifecycle defect / account-state risk:** loadUserRequests adds a listener every call, retaining no subscription and providing no cancellation/dispose or clear-on-logout. Both Home and Requests invoke it. The provider lives above AuthWrapper; signOut clears auth only. Switching tabs and users can leave old listeners able to overwrite the shared request list. Exact cross-account behavior depends on Firestore authorization and cached emissions, so do not claim a demonstrated data breach. — [Listener](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/providers/request_provider.dart:18>), [Logout](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/providers/auth_provider.dart:58>), [Provider placement](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/main.dart:32>), [Second caller](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/requests_list_screen.dart:37>)
- **Confirmed misleading notification settings:** push/email/urgent flags live only in widget state; Save Settings displays a success snackbar without persistence or backend calls. Tab changes remove the current keyed subtree, so this is not durable even for a session. EmailService exists but has no call site in lib; firebase_messaging has no corresponding implementation. — [Flags](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/profile/profile_screen.dart:20>), [Save](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/profile/profile_screen.dart:645>), [Email service](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/email_service.dart:8>), [Tab mounting](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/home/home_screen.dart:33>)
- **Confirmed pending-date reset defect in currently uncalled status method:** updateItemStatus sets purchasedDate/deliveredDate to null when resetting to pending, but copyWith uses null-coalescing and retains the old dates. This service method has no UI caller today. — [Reset intent](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/request_service.dart:61>), [Null preservation](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/models/request_model.dart:58>)
- **Race/consistency risk:** editability is checked before opening the editor, but saving rewrites all items to pending, resets aggregate status/isEditable, and does not re-read or transactionally verify current state. Another client marking something purchased during the edit could be overwritten if backend rules permit. Likewise status updates read then overwrite full arrays. — [Pre-open check](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/requests_list_screen.dart:54>), [Edit save](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/edit_delete_request_screen.dart:123>), [Direct update](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/request_service.dart:127>)
- **Confirmed dead lock-message condition:** weekday >= Sunday AND <= Wednesday can never be true (7 versus 3), so the specific lock-period explanation is unreachable. Actual model gate uses explicit OR comparisons and still restricts editing. — [Impossible message condition](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/requests_list_screen.dart:57>), [Real gate](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/models/request_model.dart:121>)
- **Batch authority/race risk:** startup attempts collection reads and creation/closing before login UI. Empty/upcoming checks use read-then-add with generated IDs, so simultaneous starts can create duplicate weekly batches. Errors are swallowed to console. This also couples startup latency to backend access. — [Startup ordering](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/main.dart:19>), [Creation](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_init_service.dart:8>), [Upcoming batches](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_init_service.dart:55>)
- **Inconsistent batch selection/cutoff rules:** initialization advances delivery if Saturday cutoff passed; fallback BatchService creates next Wednesday batches even when their Saturday cutoff is already past. Current-batch stream selects earliest open without date/cutoff predicate, while getCurrentBatch requires future delivery only. Submission only checks that a batch exists. Closing runs on startup rather than a timer/server lifecycle. Model editing permits Thu/Fri/Sat, potentially beyond Saturday-noon cutoff. — [Initializer](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_init_service.dart:35>), [Fallback](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_service.dart:45>), [Stream](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_service.dart:111>), [Submission](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/new_request_screen.dart:159>), [Edit rule](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/models/request_model.dart:131>)
- **Incomplete aggregate contract:** batch totalItems starts at zero; increment/decrement methods exist but no create/edit/delete caller invokes them in lib. These methods would count requests (+1), not actual item-array length. — [Creation](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/request_service.dart:35>), [Counter helpers](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/batch_service.dart:182>)
- **Image cleanup missing:** upload occurs before request save; failed saves or later image replacement/deletion have no cleanup. deleteImage is explicitly a placeholder returning true. — [Upload-before-save](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/new_request_screen.dart:180>), [Delete stub](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/cloudinary_service.dart:36>)
- **Realtime is partial:** request list and current batch stream snapshots, but detail screen performs a one-time fetch. No app-managed offline queue, connectivity feedback, stream onError handling, or retry UX appears in these paths; do not equate SDK caching with a designed offline workflow. — [List](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/services/request_service.dart:137>), [Detail](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/screens/requests/request_detail_screen.dart:26>), [Listener](<C:/Users/John Aerol Tapales/Documents/dacs_construction_mobile/lib/providers/request_provider.dart:18>)

### Inferences
- A revival should put batch authority and valid state transitions on the server, define timezone and cutoff rules centrally, cancel user-scoped subscriptions on sign-out, and choose authenticated storage/notification contracts shared with supported products.
- The model's no-money scope is useful and intentional for a worker interface, but is not itself authorization. No claim can be made that client checks secure writes.
- Credentials embedded as public client config should not automatically be called leaked secrets; this study deliberately avoided publishing credential values. Cloudinary unsigned preset restrictions still require separate verification.

### Gaps
- No rules/index manifests or CI configuration were found among non-generated project files. Effective Firebase authorization and production deployment state are unverified.
- Clarify intended Saturday cutoff time, handling of urgent requests after cutoff, who may mark items purchased/delivered, and whether pending requests should become editable again after delivery.
