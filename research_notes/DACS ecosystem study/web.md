# DACS Web: architecture, workflow, correctness and operational risk

## What does the active web system own, and how does it connect to the other DACS projects?

### Takeaway
The web repository is the operational and financial hub, including the admin half of the native Attendance app and its shared Supabase backend. It contains two intentionally separate project ledgers; merging their data or their definitions of overhead would change business meaning. This is a source review on 2026-09-28, not a live production audit.

### Cited Findings
- Static HTML and global JavaScript, with React on Project Control, use a compatibility facade over Supabase. There is no application build pipeline; `package.json` explicitly disables build. Vercel publishes the repository root with empty build/install commands. [Architecture](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:1>), [build contract](<C:/Users/John Aerol Tapales/Documents/Dacs Web/package.json:4>), [deployment](<C:/Users/John Aerol Tapales/Documents/Dacs Web/vercel.json:1>).
- Entry points cover public marketing, owner/staff admin, design clients, construction clients, partners and receipt share intake. Construction and partner HTML share `client-management-app.js`, so both HTML surfaces must be maintained. [Entry-point map](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:13>).
- Project Control uses `folders` as jobs, `projects` as billing periods, `payroll` and `expenses` as costs, `labor_contracts` as caps, and folder-level `overhead_expenses`. Project Management uses `construction_projects`, daily rows in `weekly_bills`, and `pm_labor_contracts`. Its nullable `construction_projects.folder_id` bridge is opt-in rather than identity equivalence. [Ledger map](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:70>), [PM project save includes bridge](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/pm-admin.js:1983>).
- Project Control lifecycle: folder/contract → BOQ → funding periods → payroll/material/overhead costs → accomplishment → invoices → verified payment requests; extra scope uses child folders. This is distinct from PM's cost-plus/direct-cost and management-fee workflow. [Lifecycle](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:125>), [fee edit and unpaid rebilling](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/pm-admin.js:1972>), [PM overhead definition](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0035_weekly_bill_overhead.sql:8>).
- Native Attendance's administrative screens, account creation, reports, sites, schedules and reward evaluation live in `attendance-admin.js`; native sign-in is implemented in `attendance-signin`, with worker/teamLeader checks, inactive-account rejection and throttle RPCs. Admin account provisioning is shared through `admin-create-user`. [Attendance module map](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:119>), [worker provisioning](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:2520>), [sign-in](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/attendance-signin/index.ts:82>).
- The shim maps collection names, camelCase and special JSON/timestamp/child-table data to Supabase; unknown ordinary fields need database columns. On-snapshot listeners requery when tables change. Parent/child invoice tables are joined on reads. [Registry and conversion](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:66>), [query/listener](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:317>).
- Web service worker handles push and receipt share POSTs only, explicitly without offline app caching. Share intake uses a dedicated Cache API store and diagnostics before redirecting to the upload screen; this should not be described as full offline support. [Service worker](<C:/Users/John Aerol Tapales/Documents/Dacs Web/service-worker.js:1>).
- Cloudflare AI is a separate worker, and nightly push is another worker with privileged Supabase reads. These operational services add deployment boundaries beyond Vercel and the two Supabase Edge Functions. [AI frontend endpoint](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/ai-summary.js:9>), [notification scheduler](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:20>).

### Inferences
- Prioritize stable backend contracts and explicit ledger identity over framework migration. Current cross-module coupling is substantial, and a UI rewrite would not itself repair authorization or transaction boundaries. [Facade](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:505>), [two ledgers](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:70>).
- The separate Flutter/Firebase project should not be treated as a current integration contract: the coordinator received the user's explicit confirmation that it is an unused prototype. The Android TWA under this web repo is also documented as dormant, distinct from native Attendance. [TWA status](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:7>).

### Gaps
- No deployed site/version, production schema, live data, notification delivery, end-user accounts or device behavior was inspected. No sign-ins or production writes were performed.
- This was a focused source study of architecture, shared data layer, authorization, finance functions/tests, migration boundaries, services and admin integration; not every line of the 31 JavaScript files or all HTML handlers was reviewed. Procurement, appointments, testimonials, agreement-document rendering, client payment lifecycles and full closeout/warranty workflows were mapped primarily through docs/tests rather than exhaustively traced end-to-end.

## Are the financial rules and current verification reliable?

### Takeaway
The central financial semantics are unusually well documented and protected by live-function regression tests. All nine configured suites and all 43 syntax checks passed locally, but these are not proof of database policies, multi-request atomicity or production schema parity.

## Which concrete issues deserve attention, and what needs clarification?

### Takeaway
The most consequential source-level concerns are privileged account provisioning, project authorization in push subscriptions, and nontransactional financial saves. These deserve controlled verification ahead of cosmetic work. Severity below assumes the deployed backend matches the checked-in source; no production exploit was attempted.

### Cited Findings
1. **High — account-creation endpoint trusts a caller-chosen tenant.** The endpoint verifies caller JWT and accepts owner/staff, but reads only caller `role`. It blocks staff creating `owner` and otherwise accepts the requested role, then persists `owner_id: body.ownerUid ?? null` through service-role access. It never derives or checks ownerUid against the caller's tenant. A staff caller can therefore request a new `staff` profile under another known owner. That created profile's `data_owner_id()` resolves to the chosen owner and `can_access()` accepts it for payroll/expenses/folders. This is a concrete source-level authorization chain, not merely missing client validation. UI callers correctly supply their current owner, but the endpoint cannot trust the UI to constrain a direct caller. [Caller gate](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:45>), [role gate](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:68>), [trusted owner field](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:97>), [tenant resolution and access](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:21>), [ordinary UI owner assignment](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:2530>).
2. **High — push subscriptions do not bind recipients to permitted projects.** project_id is arbitrary text, with no FK/access check. Admin policy accepts any owner/staff for all subscription rows, while self policy accepts any authenticated user's own row without checking project or audience. The scheduler uses a service-role client to fetch each chosen project and sends its financial metrics without checking current profile, tenant, project access or staff status. This creates both a possible cross-project disclosure path and a staff-money notification path. The ordinary admin bell has no staff guard; staff can opt in to financial summaries despite screen hiding. [Table/admin policy](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0011_push_subscriptions.sql:5>), [self policy](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0012_push_partner.sql:11>), [UI subscription](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/push-notify.js:71>), [bell visibility](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/push-notify.js:178>), [scheduler processing](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:37>), [financial payload](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:113>), [service-role request](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:187>).
3. **High/medium depending on confidentiality intent — hiding amounts does not remove API access.** Payroll and expenses policies allow staff access to full owned-tenant rows; the shim issues select(*). Similarly the original profiles policy exposes profile rows to all authenticated accounts, and the 0019 profile-update policy allows all owner/staff to update profiles without tenant scope (the trigger protects role/owner changes, but not ordinary fields/status). These are source policy facts. If this is a deliberately single-company system whose staff can encode financial values, UI-only masking may be intentional; it is not a confidentiality boundary. [Cost policies](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:117>), [full-row selection](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:317>), [profile read](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:81>), [profile admin update](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0019_admin_profile_updates.sql:39>).
4. **High for accounting durability — facade batches and nested invoice saves are not atomic.** `batch.commit()` awaits each write separately with no rollback. `writeChildren` deletes old child rows, ignores the deletion result, then inserts replacements and throws on insert failure. Thus failure after deletion can leave an already-updated invoice without its lines; failure of the delete can also cause unwanted duplicates when insert succeeds. The source establishes the failure path; no failure was injected against production. [Invoice children registered](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:125>), [parent write followed by children](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:423>), [replace logic](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:478>), [batch](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:518>).
5. **Medium — AI worker has no request authentication or application rate limit.** CORS returns headers but never refuses a POST; all vercel.app origins are included. Request body selects the model and max_tokens without an upper bound. A local in-memory test with a stub AI binding, no Authorization header and no Origin returned HTTP 200 and forwarded model `chosen-by-caller` and max_tokens 999999. This proves handler behavior, not production reachability or provider acceptance of those values. Risk is unauthorized resource consumption; no data-exfiltration claim is made. Frontend points to a concrete worker URL, but the review did not call it or verify deployment configuration. [CORS](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker/worker.js:25>), [handler and AI invocation](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker/worker.js:38>), [configured endpoint](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/ai-assistant.js:10>).
6. **Medium — new-user creation can leave a stranded Auth account.** Auth user creation succeeds before profile upsert; profile failure returns 400 without deleting or repairing the Auth account. A retry is then rejected as duplicate. This is an observable source failure path, not a reproduced incident. [Provisioning sequence](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:88>), [profile error](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:113>).

### Inferences
- First remediation track: server-derive tenant on account creation, explicitly whitelist grantable roles by caller, and constrain push subscription writes plus delivery by actual current project/recipient authorization. Validate in staging with owner, staff, worker, client and another owner. [Provisioning](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:52>), [push policies](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0012_push_partner.sql:11>).
- Second track: move compound financial saves into transaction-backed backend operations, including invoice parent/lines and critical multi-record mutations; test failures between operations. Preserve all current money invariants. [Nested writes](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:478>).
- Third track: reconcile docs/migration history against a read-only deployed inventory, update stale architecture statements, and define release ownership for Vercel, Edge Functions, Cloudflare workers and native Attendance. [Migration ledger](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/README.md:8>).
