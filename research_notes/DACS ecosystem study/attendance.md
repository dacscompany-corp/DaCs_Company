# DACS Attendance software study

## What is the product, architecture, and cross-repository contract?

### Takeaway
The Attendance workspace is a native Android worker application; its administration, authoritative data rules, and database migrations live in Dacs Web. It is a separate attendance-and-bonus reporting product, not a payroll calculator. Its offline evidence queue is the most important reliability boundary.

### Cited Findings

## How reliable and secure are capture, offline operation, authentication, and staff access?

### Takeaway
The design carefully separates durable local capture from server acknowledgement, and defends against casual time/location manipulation. Static review nevertheless identified inconsistent offline identity handling in the project picker, possible simultaneous drains despite intended serialization, and UI-only protection of staff bonus amounts.

### Cited Findings
- Every submission is first written to a Room pending row, mirrored locally, and scheduled; photo preparation occurs before queue insertion. Worker ID, pair of project identifiers, capture/trusted times, location metadata and offline state persist with the row. [Offline submission](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:76>)
- Queue draining uses the current authenticated worker ID and only that worker's sendable rows. Success caches the server row, deletes the queue row, then deletes the local photo. Permanent failures are retained and marked, transient/update/session failures retry. ### Inferences
- **High-confidence static issue, not device-reproduced:** root can restore a worker using cached identity during RefreshFailure, and attendance repository uses the same cache fallback; project repository instead derives empty worker ID from currentUserOrNull. Existing per-worker cached projects are then missed in exactly the refresh-failure/offline state the root permits. [Root identity fallback](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/SupabaseAuthRepository.kt:162>) [Attendance fallback](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:65>) [Picker identity](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:274>)
- **Reliability risk:** one-time and periodic drains have different unique work names, and both run SubmissionWorker. No shared mutex or row claim was found in the drain. Therefore comments promising only one attempt in flight are stronger than the scheduling guarantee; overlapping uploads remain possible, though server event idempotency protects records. [Names](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionScheduler.kt:17>) [Periodic worker](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionScheduler.kt:131>) [Drain selection](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionWorker.kt:102>)
- **Stale cache risk:** a successful empty project list is returned without clearing the old cache, so a later network failure can resurface retired projects; backend still validates submissions, preventing silent acceptance but potentially causing worker-visible failure. [Cache replacement condition](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:276>)
- **Policy ambiguity:** current staff amount hiding satisfies presentation-only restriction, not strict data confidentiality. Clarify whether “staff must not see peso amounts anywhere” also prohibits network/API retrieval before prioritizing a redesign. [RLS](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0066_attendance_weekly_reward.sql:119>)

### Gaps
- No live RLS/storage policy check, handset/emulator test, offline/reboot simulation, or modified-client penetration test was performed. Findings above are code evidence and explicitly marked risks, not claims of exploited production behavior.
- Product decisions needed: must location be tied to shutter time? What review/appeal path handles legitimate unverified days, missed Time Out, or an offline reboot that destroys the trusted clock anchor? How are unrecoverable local failures reconciled by an administrator? Who owns photo retention and cleanup of abandoned captures/uploads?

## What was verified and what should happen next?

### Takeaway
Existing test coverage is broad in pure rules and some view models, but a fresh test run could not start in this environment. Stabilization should prioritize cross-repository contracts, the offline picker identity mismatch, and actual handset scenarios over new feature work.

These priorities follow the concrete references in the preceding sections.

### Gaps

- Questions for the owner: (1) Is staff amount access forbidden in APIs as well as screen/exports? (2) Who approves disputes/bonus exceptions and can a frozen week ever be corrected? (3) What are actual worker device and signal conditions, and which app versions remain installed? (4) What is the APK upgrade and rollback process, including who holds signing material? (5) Is attendance intended eventually to connect to payroll, or must isolation remain permanent?
