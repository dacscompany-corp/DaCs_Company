# DACS platform, data, authorization, infrastructure and maintenance

## What is the platform and what did this review cover?

### Takeaway
This is a substantial static web business system, not a conventional bundled frontend: six HTML applications share a handwritten Firestore compatibility layer over Supabase, with one directly edited React screen. Reading started September 26 and concluded September 27, 2026 (Asia/Manila). Baseline Git HEAD was `dc2c70fcf816580a8a27d3c360ceb176fb351dae`; `git status --short` was clean before research files were added (global Git ignore-file permission warnings do not establish additional repository modifications).

### Cited Findings
- Six entry points: public marketing/appointments/testimonials (`index.html`), back office (`admin.html`), design-client portal (`client.html`), construction-client portal (`Client Management.html`), partner portal (`Dacs Partnership.html`), receipt intake (`share-capture.html`). Construction and partner pages share `client-management-app.js`; both must be kept in sync. [Architecture](../../docs/ARCHITECTURE.md:15)
- Runtime is plain HTML/vanilla JS, React 18.3.1 via CDN for Project Control, Supabase JS v2 CDN, Chart.js 4.4.0 and Lucide latest. Admin loads 29 local scripts, most eagerly, including the directly edited compiled portal. Dependency order matters: Supabase before shim, allocation engine before money modules, React before deferred portal. [Scripts](../../admin.html:5371), [React](../../admin.html:5412)
- Seven primary navigation groups: Project Control, Project Management, Attendance, Quotations, Appointments, Construction, Users. Their subviews include reports, BOQ, invoices, payments, overhead, reimbursements, closeout, warranty, worker sites/schedule/rewards, appointment analytics/feedback, procurement batches/urgent/history/inventory and people. [Navigation](../../js/admin.js:2191)
- `android/` is a dormant client-portal Bubblewrap wrapper, whereas `android-receipt-share/` is an active source family for native receipt handoff into the existing web wizard. The separate native attendance app is outside this repository. Wrapper deployment/device status is documented, not independently device-tested here. [Architecture](../../docs/ARCHITECTURE.md:7), [Receipt app](../../docs/RECEIPT_SHARE_APP.md:35)
- Backend source families include 82 SQL migration files (highest 0074), SQL verification scripts, two Supabase Edge Functions (`admin-create-user`, `attendance-signin`), and two Cloudflare workers (AI proxy and scheduled notifications). Migrations contain 36 initial public tables plus later domains; duplicate `CREATE TABLE IF NOT EXISTS` declarations mean a raw occurrence count is not a live table inventory. [Initial schema](../../supabase/migrations/0001_init.sql:26), [Latest migration](../../supabase/migrations/0074_billing_allocation_owner_check.sql:1)
- This assigned review read architecture, shim, auth/navigation, representative foundational and later SQL security migrations, backend services, notification/PWA code, dependency/deployment configuration, maintenance docs and user management. Finance, PM, public/client and attendance domain details are assigned to other researchers. Only notes were added; no application edits, build, production queries, deployment or schema writes occurred.

### Inferences
- The system behaves as multiple applications sharing globals, data conventions and handwritten contracts. The primary maintenance risk is drift between independent screens/exports/services, not a missing build pipeline.
- A modernization should preserve the static workflow and financial invariants; introducing a framework is not prerequisite to fixing concrete risks.

### Gaps
- This is a source review, not proof of current production deployments, credentials, active policies, migration history, browser behavior or external native attendance functionality. Android, TypeScript Edge Functions, inline HTML scripts and SQL were not compiled/executed in this assignment.

## How does data access, identity and authorization actually work?

### Takeaway
The shim is central and fairly sophisticated but deliberately incomplete compared with Firestore. Database security protects rows and selected isolated modules; much staff money hiding and all module-focus behavior are presentation restrictions rather than backend confidentiality boundaries.

### Cited Findings
- `REG` maps logical collections to physical tables, aliases `userId` to `owner_id`, discriminates `profiles.kind`, wraps timestamps, and expands invoice/request children. `SUBREG` flattens nested PM collections onto tables using project foreign keys; revolving fund is a singleton keyed by project, and daily logs/milestones/accomplishment/walkthroughs/partner agreements use JSONB data blobs. [Registry](../../js/supabase-config.js:68), [Subregistry](../../js/supabase-config.js:159)
- Regular fields become snake_case columns; unknown fields cannot simply be persisted. JSONB tables instead store non-system data in `data`. On read, `kind` is hidden only for actual discriminator collections, preventing historical quotation preset/payment/error field loss. Child rows are returned sorted by position. [Conversion](../../js/supabase-config.js:184), [Read conversion](../../js/supabase-config.js:215)
- Query builder supports where/order/limit and selects `*`; JSONB collection filters/sorting/limits are performed locally after fetching the parent collection. There is no pagination loop in `.get()`. Collection realtime listens to all table changes, then reruns the entire query; every subscriber has its own channel. [Query implementation](../../js/supabase-config.js:310)
- `DocRef.get/update/delete` scope by primary/singleton key and parent context. `set(data, opts)` ignores `opts` and performs an upsert. JSONB updates read, merge in JS, then overwrite the blob; concurrent writers can lose unrelated changes. Updates do not request affected-row counts, so a zero-row update can appear successful. [Document implementation](../../js/supabase-config.js:382)
- **Confirmed latent code defect:** `DocRef.onSnapshot` calls `this._pk()` even though the class defines `_keyCol()` and `_keyVal()`, not `_pk`. It would throw when invoked. A repository-wide `.onSnapshot` scan found only collection/query production subscriptions (including nested notification `.collection('items')`); no current reachable direct document subscription was established. Do not describe this as an observed production outage. [Defect](../../js/supabase-config.js:467)
- **Confirmed non-atomic behavior:** `db.batch().commit()` loops through independent operations; no rollback/SQL transaction. Parent and child saves are separate operations. Child replacement deletes existing rows then inserts new rows; the delete result is not checked. Partial failure is possible even when callers assume Firestore-like batching. [Children](../../js/supabase-config.js:478), [Batch](../../js/supabase-config.js:505)
- Auth facade stores/refreshes Supabase sessions, maps users to legacy Firebase shape, and deduplicates same-UID auth callbacks to avoid rendering again on tab focus/token refresh. Signup, password login/reset, reauthentication and password updates use Supabase; admin account creation calls an authenticated Edge Function. `serverTimestamp` conversion uses browser `new Date()` rather than a database server clock. [Auth](../../js/supabase-config.js:562), [Timestamp write](../../js/supabase-config.js:208)
- Auto-provision trigger creates an ordinary active client profile on auth-user insertion. Role policies derive from the profiles table, not user-editable metadata. `can_access` permits own records or staff records belonging to their assigned owner. Several older operational tables use broad owner/staff predicates rather than tenant ownership. [Provisioning](../../supabase/migrations/0003_auth_hooks.sql:11), [RLS helpers](../../supabase/migrations/0002_rls.sql:7), [Operational policies](../../supabase/migrations/0002_rls.sql:163)
- **Staff money privacy is presentation-level:** expenses/payroll rows are accessible through `can_access`, and migration 0006 explicitly permits staff to read their owner's contract value because cost amounts already exist in the browser. Hiding peso cells is not equivalent to preventing data retrieval. [Money rows](../../supabase/migrations/0002_rls.sql:117), [Explicit staff budget rationale](../../supabase/migrations/0006_folder_budgets_staff.sql:1)
- **allowed_modules is navigation focus:** the field migration only adds JSONB, JS filters navigation and subviews, and inline admin switchView enforces redirects. No RLS predicate references allowed_modules in the inspected migrations. This matches its documented module-focus purpose; it should not be represented as a strong authorization feature. [Column](../../supabase/migrations/0009_profile_allowed_modules.sql:1), [Focus](../../js/admin.js:2269), [Route guard](../../admin.html:6296)
- Actual navigation dispatch is the inline `window.switchView` in admin.html, overriding admin.js. It tears down registered view listeners, blocks staff from Users/Clients/System Errors/PC Reports/Reimbursements/Warranty/Quotations, limits workers to construction batches/urgent/history, then applies focus. Multiple permission surfaces must remain synchronized. [Dispatcher](../../admin.html:6259)
- **Confirmed deactivation gap:** User Navigator toggles only profile status. Web admin authentication reads role and agreement, but does not reject inactive status; the foundational `auth_role()` helper also ignores status. In contrast, attendance-signin explicitly rejects inactive workers. A web account's deactivate action therefore does not establish revocation in inspected source. Live/session behavior remains to verify. [Toggle](../../js/user-navigator.js:179), [Web login](../../js/admin.js:23), [Role helper](../../supabase/migrations/0002_rls.sql:7), [Attendance check](../../supabase/functions/attendance-signin/index.ts:156)
- **Confirmed UI/backend role-edit conflict:** employee edit sends `{displayName, role, position}`; profiles_guard allows role changes only between client/partner, and forbids changing privileged roles through the ordinary client. A changed employee role will be rejected if these migrations are deployed. [Edit](../../js/user-navigator.js:306), [Guard](../../supabase/migrations/0019_admin_profile_updates.sql:16)
- Profile SELECT is available to every authenticated user, and self-update guard protects role/owner_id but does not generally lock all identity/configuration fields. This warrants a dedicated profile field/tenant review; do not claim arbitrary owner escalation since the guard explicitly prevents it. [Policies](../../supabase/migrations/0002_rls.sql:83), [Guard](../../supabase/migrations/0019_admin_profile_updates.sql:16)
- Admin-create-user verifies JWT and owner/staff role, prohibits staff minting owners, refuses duplicate auth emails, then creates Auth user and separately upserts a whitelisted profile. There is no cleanup of an Auth user if profile upsert fails, and no caller status/module-focus test. [Function](../../supabase/functions/admin-create-user/index.ts:45), [Creation](../../supabase/functions/admin-create-user/index.ts:94)
- Private uploads are signed for one hour with cached URLs refreshed before expiry. Global fetch/window.open/click/image/iframe behavior converts stored public-format identifiers to signed URLs. Storage reads remain permitted to **any authenticated user for the whole uploads bucket**; insert also broad, overwrite restricted to owner/staff by 0032. This blocks anonymous reads and client overwrites, but is not per-project document isolation. [Signing](../../js/supabase-config.js:682), [Read/insert policies](../../supabase/migrations/0027_private_uploads.sql:29), [Overwrite restriction](../../supabase/migrations/0032_uploads_no_overwrite.sql:38)
- Agreement evidence freezes PDFs, SHA-256 hashes and append-only acceptance events. SQL trigger rejects event updates/deletes even by service role. However snapshot/log helpers intentionally fail open (warnings and acceptance continues); the employee gate itself catches errors and continues. Audit completeness is therefore best effort, not guaranteed. [Evidence helpers](../../js/supabase-config.js:807), [Event table/trigger](../../supabase/migrations/0021_agreement_events.sql:18), [Gate catch](../../js/admin.js:70)

### Inferences
- Priorities: clarify whether staff must merely not see amounts in normal UI or must be technically unable to retrieve them; implement explicit inactive-account enforcement; review document/project entitlement and profile permissions; move critical multi-record transitions to transactional RPCs where required.
- Unpaginated queries and full-table realtime notifications may produce truncated datasets or excessive refetches as data grows. This is a code-level scalability risk; current row counts/server row limits were not inspected.
- JSONB read/merge/write needs optimistic concurrency or an atomic update strategy if multiple editors touch the same records.

### Gaps
- No live RLS test, schema reset/replay, role matrix, multi-owner fixtures, JWT revocation test or storage signing test was run. Historical documentation explicitly reports live schema drift, so migrations are intended state, not proven live state.

## How do services, operations and the maintenance safety net behave?

### Takeaway
The platform already has useful operational support—realtime, telemetry, push, receipt intake and pure-function tests—but deployment/runtime parity and authorization at service boundaries need attention. Syntax passed for all 46 checked authored JS files; CI runs only three of nine npm test suites.

### Cited Findings
- Vercel serves repository root with empty install/build commands. `npm run build` intentionally fails because portal compiled JS is the maintained source. No build was run. [Deployment](../../vercel.json:1), [Scripts](../../package.json:1)
- Service worker has **no general offline caching**. It immediately activates/claims clients, intercepts only POST share-capture, stores temporary receipt files and diagnostic metadata in Cache API, redirects to wizard, and handles push/notification clicks. Do not describe this PWA as an offline financial application. [Service worker](../../service-worker.js:1)
- Cache busting is manual and inconsistent: some admin scripts have date query strings, others no version; remote Supabase uses major-only v2, Lucide uses latest, React development builds are shipped. These are reproducibility/performance risks, not proof of a current failure. [Script tags](../../admin.html:5371), [React](../../admin.html:5412)
- Receipt Android wrapper loads the production wizard in a WebView and exposes native files as `DacsNative`; it retains separate WebView login/session. Kotlin navigation tests URL string prefixes rather than parsed exact scheme/host. This is a hardening opportunity because lookalike origins can share a prefix; actual malicious navigation was not tested. [Wrapper](../../android-receipt-share/app/src/main/java/app/dacs/receiptshare/ShareActivity.kt:40), [Navigation](../../android-receipt-share/app/src/main/java/app/dacs/receiptshare/ShareActivity.kt:69)
- Two Cloudflare services are distinct. AI proxy calls Workers AI Llama 3.1 8B (not Groq, despite stale frontend comments), accepts chat messages, model and token/temperature overrides, and returns OpenAI-shaped JSON. It has CORS behavior but no authentication or rate/size restriction in source. CORS is not server-side caller authorization. [AI worker](../../cloudflare-worker/worker.js:24), [Request handler](../../cloudflare-worker/worker.js:38)
- AI is wording/reporting assistance, not an accounting writer. The browser sends names, financial metrics and detected issues to the worker; output is escaped before display. **Confirmed inconsistency:** ai-summary computes Spent as labor + material and ignores overhead even though portal passes overhead. Its displayed/prompted spent can disagree with canonical totals. [Summary](../../js/ai-summary.js:131), [Caller](../../js/portal-app.compiled.js:808), [Health briefing](../../js/ai-assistant.js:217)
- Scheduled push worker reads subscription rows using service-role credentials, groups by project, computes costs/paid/progress/fund balance and emits separate admin or partner metrics. Dead 404/410 subscriptions are deleted. It also exposes a trigger-key protected manual run/debug endpoint. Cron time is documented as 15:59 UTC = 23:59 Philippine time; deployment schedule itself was not inspected. [Worker](../../cloudflare-worker-notify/worker.js:19), [Metrics](../../cloudflare-worker-notify/worker.js:83)
- **Confirmed missing notification entitlement check in source:** `push_subs_self` checks only that owner_id is current user, with arbitrary project_id text. Service-role notification worker then computes metrics for each subscribed project without rechecking the subscriber's project membership. This is an authorization risk across clients/projects if deployed as written. Staff also fit broad admin subscriptions and receive monetary admin summaries; no recipient-role filtering is present. [Subscription schema/policy](../../supabase/migrations/0011_push_subscriptions.sql:5), [Self policy](../../supabase/migrations/0012_push_partner.sql:11), [Service read/send](../../cloudflare-worker-notify/worker.js:38), [Money messages](../../cloudflare-worker-notify/worker.js:107)
- Browser push owner ID can be currentDataUserId (staff owner's ID) rather than acting staff UID, and stored rows default admin audience. This makes later actor-role filtering harder without recording recipient identity explicitly. [Identity](../../js/push-notify.js:41), [Store](../../js/push-notify.js:70)
- Attendance-signin is an explicit native login boundary with email-based throttle RPCs, service-key password authentication to bypass web captcha requirement, role/status checks and session revocation on rejected roles/status. Native attendance domain RPC semantics are covered by another researcher. [Signin function](../../supabase/functions/attendance-signin/index.ts:74)
- Error telemetry reports uncaught JS/rejections, dedupes and caps 15 records per browser session, limits text length, ignores opaque cross-origin Script error. Owner can read latest 200 and clear errors. SQL insert accepts anon/authenticated and constrains lengths but does **not** enforce a 15-record server rate limit. Quiet telemetry is not proof all flows succeeded, especially caught-and-warned failures. [Reporter](../../js/supabase-config.js:858), [SQL](../../supabase/migrations/0028_client_errors.sql:38), [UI](../../js/error-log.js:21)
- Realtime migration explicitly adds current public tables to publication; new tables need explicit publication treatment. The shim subscriptions are not sufficient by themselves to make a table realtime. [Publication](../../supabase/migrations/0004_realtime.sql:1)
- **Verification performed:** `node --check` passed for 46 files: 31 application JS files, 9 tests, 2 Cloudflare workers, 3 BOQ import tools, service-worker.js. This verifies parseability only. Finance researcher runs npm test; see their exact totals/result rather than assuming syntax implies behavior.
- **Confirmed CI gap:** package npm test includes money, reimbursement, quotation, quotation-PDF-import, shim-fromrow, shim-docref, folder completion, attendance, billing allocation. CI syntax checks only js/*.js and tests/*.js, then executes only money, reimbursement and billing allocation. Thus six suites run locally but not in CI; workers/service worker/import scripts are outside its syntax loop. [Test script](../../package.json:3), [CI](../../.github/workflows/ci.yml:35)
- Migration README's next-number line says 0053 while disk reaches 0074; status ledger contains old pending/unverified statements. Architecture correctly says highest 0074 and acknowledges uncaptured weekly_bills field drift. README is useful for duplicate/gap ordering but cannot establish applied state. Nine duplicated numbers and deliberate missing 0034 are historical, not newly discovered missing migrations. [Migration guide](../../supabase/migrations/README.md:8), [Ledger](../../supabase/migrations/README.md:47), [Architecture traps](../../docs/ARCHITECTURE.md:164)
- Additional documentation drift: schema doc introduces Supabase but retains a “Firestore is schemaless” field-map note and labels folder budgets confidential despite explicit staff-read migration. CI comment says 46 money checks although test implementation has evolved. Source and migrations should override stale prose; do not silently rewrite documented business decisions. [Schema](../../docs/DATABASE_SCHEMA.md:1), [Budget label](../../docs/DATABASE_SCHEMA.md:94), [CI comments](../../.github/workflows/ci.yml:6)
- Package lock is explicitly ignored; dev dependency ranges exist despite runtime being CDN-based. Future tooling installs are not fully reproducible from tracked root package metadata alone. [Ignore](../../.gitignore:42), [Dependencies](../../package.json:8)

### Inferences
- Recommended sequence for a later authorized implementation: (1) confirm production RLS/migration baseline; (2) enforce account deactivation and notification project entitlement; (3) repair staff-display regressions and AI arithmetic against shared functions; (4) run all nine suites in CI and syntax-check remaining authored JS; (5) improve transactionality/concurrency/pagination; (6) reconcile deployment and migration documentation.
- PWA/Android receipts, AI, and nightly notifications are separate operational contracts that can drift from the core app. Include them in financial/privacy review and release checklists.

### Gaps
- No claim is made about live vulnerability exploitation, server secrets, current cron health, Vercel deployment matching HEAD, backup/recovery readiness, production error counts or current library support. No credential values were copied into these notes. UI/browser tests, migration replay, cross-tenant security fixtures and deployed service inspection remain separate verification work.
