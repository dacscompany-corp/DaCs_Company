# Client appointments: database, security, integration and verification

## What data is stored, and what reaches the admin browser?

### Takeaway
The module is one standalone `appointments` table, with no client/profile/project relation. The public wizard writes SQL column names directly; admin reads through the shared compatibility shim. Migration 0084 is required for the current wizard and also closes a historical authenticated-wide privacy exposure.

### Cited Findings

There are no appointment-specific `NOT NULL`, status enum/check, string-length, contact-format, slot uniqueness, ownership or foreign-key constraints beyond UUID PK and unique legacy id. — [0001_init.sql:569](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0001_init.sql:569>)

- Public `buildRow` writes 13 explicit columns: caller-generated UUID, trimmed name/email/contact/message/location, service, meeting/property/budget, preferred date/time, and status pending. ### Inferences
- Full-row queries can stop at the configured Supabase API row cap and thereby omit older appointments/understate analytics once the table outgrows that cap. The actual project cap is unknown.
- Six hex characters give 24 bits of reference space. Distinct UUID rows may share a displayed reference, so reference alone should not be treated as a unique lookup/security token. Do not add a public reference lookup without authorization/privacy design.
- UUID column typing rules out stored JavaScript payloads in `appointments.id` under the repository schema. Caller choice of UUID does not permit quote characters. Do **not** report id-based inline-handler XSS from this schema; live type drift has not been inspected.

## Which permissions and integrity guarantees are actually enforced?

### Takeaway
Effective repository policies after 0084 permit anyone to insert and only owner/staff to read/update/delete. The important remaining gap is that public inserts are unrestricted by business rules: callers can bypass pending status and all wizard validation. Staff budget hiding and module focus are frontend controls rather than database confidentiality/authorization boundaries.

### Cited Findings
- Chronology: 0002 enables appointments RLS, creates permissive `appt_create FOR INSERT WITH CHECK (true)`, `appt_read FOR SELECT USING (auth.uid() is not null)`, and `appt_admin FOR ALL USING/WITH CHECK (is_owner() or is_staff())`. No `TO` restricts these policies, so their target is PUBLIC. — [enable RLS:64](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:64>), [policies:299](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:299>)
- 0084 drops only `appt_read` and keeps public insert/admin management intact. This removes all signed-in clients/partners/workers' broad SELECT access supplied by that policy. No other appointment-policy alterations were found across migrations. — [0084:19](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0084_appointments_booking_details.sql:19>)
- Result under these migrations **and suitable table grants**: anonymous and non-admin authenticated accounts may insert any row accepted by SQL types/PK; they cannot read/update/delete existing rows. Owner/staff may select/update/delete every appointment, without tenant ownership or `allowed_modules` restriction. `is_owner`/`is_staff` consult the server-side `profiles.role` using `auth.uid()`, not user-editable JWT user metadata. — [helpers:7](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:7>), [appointment policy:299](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:299>)

### Inferences
- **P1 — public status/integrity bypass, confirmed source configuration:** an anonymous caller can submit an appointment with `status:'completed'` or `'confirmed'`, null required contact fields, arbitrary services and past/Sunday schedule. SQL date typing rejects impossible date syntax, but not valid past dates/business-rule violations. Caller can supply `created_at`/`updated_at` instead of accepting defaults, distorting creation-date ordering/analytics. UI sets pending; the DB does not enforce it. Assess tightening public INSERT CHECK/column privileges and server-side validation while keeping legacy nullable-row compatibility. A live exploit was not executed.
- **P1 if 0084 is absent — PII exposure/deploy dependency:** older policy allows every signed-in account to read all visitor names/emails/phones, and current wizard writes unknown columns if migration is missing. Verify live columns AND policy removal before asserting production is healthy. This is a conditional risk, not a claim that 0084 is missing.
- **P2 — staff budget accessible through API:** current UI obeys visual hiding but database does not enforce confidentiality of peso-labelled budget ranges. Decide whether the rule means display suppression or true read restriction; the latter requires a separate restricted storage/read surface or carefully scoped column access.
- **P2 — spam/oversized-row abuse:** an unrestricted direct database insert path means browser rate guards/validation can be bypassed. Repeated large arbitrary rows could pollute admin views and consume resources. Edge-platform protections, if configured externally, are unverified; no appointment backend guard exists in repository source.
- **P2 — concurrent/zero-row false success:** two admins can overwrite status changes with last-write-wins; a deleted or newly inaccessible row can yield an error-free zero-row operation while admin shows success. Consider returned affected-row verification and a compare/version condition if workflow contention matters.
- **P2 — ambiguous retry duplicates:** if the DB commits but the response is lost, retry generates another UUID and can create the same request twice. Persist/reuse one id for retries or implement server idempotency; currently one-click guarding only covers the active request.
- **Design clarification:** global appointments may intentionally be a single-company inbox. Missing owner/tenant scope is not automatically a defect without a multitenant product requirement. Likewise `allowed_modules` currently promises navigation focus, not a server permission boundary; avoid overstating that as a newly introduced bypass.

### Gaps
- Actual live table grants/policies/types, any manually added constraints/functions, Supabase/network gateway throttling and production activity/error logs are unknown. Source security conclusions assume migration replay and no unrecorded drift.
- Any PII retention/deletion policy, audit trail requirement, staff confidentiality intent beyond the UI rule and multi-owner tenancy requirement were not supplied. Appointments retain only current status/timestamps, not an actor/status-history table, under the migrations cited above.

### Inferences
- **P2 — stale/realtime failure:** a visitor request can refresh dashboard counts while an already-open appointment table remains stale until its render/filter/navigation is triggered. Table refresh should preserve active filters. Silent subscription/read failures make operational detection weak.
- **P2 — verification gap:** meaningful next tests are DB role allow/deny for anonymous/client/partner/worker/staff/owner; adversarial non-pending public insert; absent migration behavior; returned-row-free insert; zero-row updates; network timeout/retry; duplicate requests; and realtime/table filter preservation. - Channel queries can overlap and return in a different order; shim has no generation ordering to prevent older results replacing newer snapshots. It performs full re-queries rather than applying individual changes.
