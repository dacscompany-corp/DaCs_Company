# Client appointments: admin workflow, navigation, reliability and notifications

## How does the admin side receive and manage appointments?

### Takeaway
The module is a public-intake inbox and simple status register. It presents booking preferences and contact information but does not implement a reservation calendar, confirmed meeting schedule, assigned case owner, outbound confirmation service, editable appointment details, or a conversion to a client/project.

### Cited Findings
- Entry point and global state: `admin.html` loads `js/admin.js`; appointments and current modal selection live in top-level mutable arrays/objects. Sign-in checks an admin profile, active account status and owner/staff/worker/teamLeader role before starting the dashboard. [State and authentication](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1>)
- The Appointments primary section contains Dashboard (hidden secondary pill), Appointments, Analytics and Feedback; its default is Dashboard. Normal owner/staff login currently lands in Project Control; an `allowed_modules:['appointments']` focus lands in the Appointments dashboard. [Primary nav](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:2264>), [Default role landing and focus override](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:406>), [Focused allowed views](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:2309>)
- Staff may use all four appointment views. Workers/team leaders only see Construction. Role and focus guards exist in the effective `window.switchView` in `admin.html`, which overrides the earlier `admin.js` implementation. Appointments has no drill-down route requiring an `_FOCUS_SUBVIEWS` entry; its detail overlay is opened by a direct function call. These are UI permissions, not claims about DB authorization. [Nav role filters](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:2328>), [Actual view guards](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:6264>)
- `showDashboard()` starts an appointments subscription after sign-in, replacing a previous subscription. It orders by submission `createdAt` descending and does not specify a limit, date filter, owner filter, or pagination. The separate `loadData()` uses a 200-row limit; no call to that function was found in the admin implementation. [Live subscription](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:486>), [Alternate loader](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:817>)
- Registry maps `appointments` straight to its table and wraps `createdAt`/`updatedAt` as timestamps. The shim subscription initially queries, then re-queries the entire selected table on every appointments change; it does not apply a server-side realtime channel filter. [Registry](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:154>), [Query subscription](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:357>)
- Main table columns are submission Date, Name, Email, Contact, Service, Preferred schedule, Status and Actions. Clicking a row opens details; the status dropdown stops propagation. Search matches only lowercase name/email and does not trim the query. Status filter covers all/pending/confirmed/completed/cancelled. [Markup](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:369>), [Shared row renderer](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:931>), [Filter](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:969>)
- Details add reference, meeting type, property type, budget, location, preferred schedule and freeform message, with absent optional fields omitted for old rows. Budget is hidden from staff; all public text fields are escaped using `_admEsc`. Modern and historical service IDs have labels. [Escaping](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:880>), [Optional fields and staff budget gate](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1053>), [Service labels](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1972>)
- The effective module offers no admin create/edit form, print control, CSV/PDF export, bulk action, contact action, assignment, calendar or confirmed-schedule field. The table offers only the status select; the detail footer offers Close and Delete. No appointment references were found in `js/print-utils.js`, `js/invoice-module.js` or `supabase/functions`. [Table controls](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:369>), [Detail footer](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:3787>)
- Status options permit any of the four states from any prior state, including moving completed back to pending. Saving writes only `{status, updatedAt}`, with a confirmation overlay beforehand; there is no client-side allowed transition graph, unchanged-status guard, previous-status condition, history, reason or actor field in this path. Deletion is a hard delete after a second confirmation. [Status mutation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:988>), [Deletion](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1124>)
- The status confirmation interpolates `newStatus` without escaping, but the reachable table path passes `this.value` from four hardcoded options, not the persisted arbitrary status; no source-backed public status-to-dialog XSS path was found. UUID appointment IDs also rule out a public arbitrary-text-ID attack through quoted inline handlers under the checked migration. ### Inferences
- Staff-visible freeform project details may contain visitor-written money amounts even though the explicit Budget row is hidden. This is a policy boundary needing a decision, not proof of a rendering bypass. [Details fields](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1095>)
- Last-writer-wins status updates are possible when two operators edit the same record because updates match only the ID; no compare-and-swap guard is present. - High-volume history will need explicit paging or a bounded date range; current global full-result refetch on every event plus all-row rendering is inefficient. Actual production row cap/configuration is unverified. [Live query](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:488>), [Rendering](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:965>)

### Gaps
- No browser session, production mutation or live table inspection was performed. Effective database role isolation, migration application and Supabase row limits must be taken from the data/RLS audit, not inferred from UI access.
- The manual business process for calling/emailing clients, hours of coverage and whether appointment history should be retained are unknown.

## Which defects or reliability risks are supported by evidence?

### Takeaway
The clearest operational defects are stale tables under realtime updates and filters silently discarded by refreshes. Secondary issues affect data loading visibility, deletion races, analytics and session cleanup.

### Cited Findings
- **P2: realtime changes never refresh the appointments table or open details.** The callback replaces `appointments` and redraws dashboard statistics/recent items/charts, plus Analytics/Feedback conditional views; it never invokes `displayAllAppointments`, `filterAppointments` or `showAppointmentDetails`. A newly inserted request can therefore increment the pending badge while remaining absent from the active list. Initial data arriving after the user opens the table can leave the empty state stale too. Alternative refresh paths are entering the view in either switchView implementation, filter input/change events, local status save/cancel and local deletion. Those paths do not repair cross-session realtime updates until triggered. [Callback](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:490>), [View entry](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:6338>), [Filter listeners](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:618>), [Local mutation refreshes](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:997>)
- **P2: active filters become visually misleading after mutation or navigation.** `displayAllAppointments()` ignores the status/search controls, yet view entry, cancelling confirmation, successful status update and delete all invoke it. Controls still display the selected filter/query while nonmatching rows are shown. [Unfiltered renderer](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:959>), [Cancel and save refresh](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:997>), [Delete refresh](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1139>), [View refresh](</C:/Users/John Aerol Tapales/Documents/Dacs Web/admin.html:6338>)
- **P2: appointment query errors can silently leave an empty/stale UI.** `showDashboard` supplies no subscription error callback, and the shim catch only invokes `onErr` if supplied. Thus query failure is caught and discarded; it bypasses the global uncaught-error telemetry. The alternate loader only logs errors. A failing status save shows an error toast but does not redraw the dropdown back to its persisted value. [Subscriber](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:488>), [Error swallowing](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:359>), [Status catch](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1014>), [Telemetry listens to uncaught events](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:891>)
- **P2: closing details while an awaited delete is in progress can turn a successful DB delete into an error toast.** The method reads `currentAppointment.id` again after `await delete()`, while `closeModal()` sets `currentAppointment=null`. This was reproduced with a deferred-context stub. Capturing the ID before any awaits removes the race; disabling destructive controls during the operation also helps. [Delete awaits/reuses mutable selection](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1124>), [Close clears selection](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1118>)
- **P2: both monthly charts are locked to 2026.** The Dashboard services/trend chart uses keys `2026-01` through `2026-12`; the Analytics trend uses `const currentYear=2026`. Bookings in 2027 will still count in total/pending/service/status metrics but disappear from monthly trend plots. [Dashboard keys](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1180>), [Analytics year](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1584>)
- **P3: analytics semantics need clearer labels.** “Conversion rate” is completed appointments divided by all appointments, not signed contracts or created clients/projects. “This week” is a rolling seven-day timestamp lower bound, without an upper bound. “Weekly Activity” counts weekday submissions across all loaded history, not the current week and not preferred meeting dates. Popular Service shows only the first word, causing multiple services to display “Interior”. Zero appointments exits before resetting metrics, leaving the prior conversion/growth/popular values. [Seven-day metric](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:857>), [Analytics metrics](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1512>), [Weekday histogram](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1901>)
- **P3: session cleanup comment is inaccurate.** `_appointmentsUnsub` is declared with a comment promising logout teardown, but its only operational references are start/replacement in `showDashboard`. The unauthenticated auth branch only calls `showLogin`, and logout only signs out. Cached appointments/current appointment/role are not explicitly cleared there. This is an avoidable listener/cache lifecycle issue; actual database exposure after signout is not asserted. [Unauthenticated branch](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:103>), [Logout](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:682>), [Unsubscribe declaration](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1995>)
- An appointments listener starts for every accepted admin role and focused-module account even where the UI disallows appointment views. Scope its startup to actual UI permission, while keeping RLS as the authorization layer. [Unconditional startup](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:97>), [Global dashboard subscription](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:486>)

### Inferences
- Preferred schedule is a request preference, not a reserved slot; treating confirmed status as calendar booking would create false assurances. Status is not linked to any actual assigned date/time. [Status-only save](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1005>), [Preferred schedule display](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1098>)
- Because DB update/delete only inspect `error` and request no affected row count, the UI can report success on a zero-row operation (e.g. another operator already deleted the record). This is a code property demonstrated by the shim, not a production occurrence. [Update](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:452>), [Delete](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:460>)

### Gaps
- Browser UX, mobile clipping, keyboard accessibility and network reconnect behavior were not tested in a real browser. No claim of production incidents or frequency is made.
- Focus restrictions are intentionally described as UI scoping; whether these should also narrow appointment database access is a business/security decision for the data audit.

## Are there notifications, verification coverage and concrete improvements?

### Takeaway
There is no automatic appointment confirmation or notification integration in the checked repository. The module already has useful escaping, backward compatibility, staff budget hiding and shared render helpers; focused behavior tests should protect the missing refresh/error paths.

### Cited Findings
- `updateStatus` has only a status/timestamp DB mutation and local UI refresh/toast, no email/SMS/Messenger/push/notification write. Delete likewise only deletes the appointment. [Update](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1005>), [Delete](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1130>)
- Admin notification bell loads the signed-in account’s latest 30 notification items. Its metadata map covers billing/reports/material requests/SOA/closeout, but no appointment event or destination. Repository-wide appointment search revealed no database notification trigger or Edge Function appointment handler. Accordingly, client confirmation currently depends on manual contact, despite any public wording about a response within 24 hours. [Bell load](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/construction-module.js:674>), [Event types](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/construction-module.js:747>), [Status-only update](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1005>)
- `node tests/booking.test.js` completed with **24 passed, 0 failed** on 2026-10-02. Admin cases validate service-label coverage, the staff Budget gate, shared table-row helper, Preferred header and booking-before-admin script order. They do not exercise callback refresh, filter persistence, mutation errors, concurrent edits, delete race, cleanup or analytics semantics. [Admin tests](</C:/Users/John Aerol Tapales/Documents/Dacs Web/tests/booking.test.js:162>)
- Isolated Node VM probes extracted the real functions into mock DOM/DB contexts. The realtime probe replaced the underlying array with `New client` but left table text `OLD TABLE`; invoked functions were badge/stat/recent/chart updates only. The filter probe first rendered Alice pending, then `displayAllAppointments` rendered Alice pending plus Bob completed while controls still said `pending`/`Alice`. Empty analytics retained a previous `100%`. Closing selection during mocked awaited DB deletion produced `dbDeleted:true` and an error toast with `Cannot read properties of null (reading 'id')`. These probes used no production access and created no application edits. [Functions probed](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:467>), [Table render/filter](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:959>), [Empty metrics](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1512>), [Deletion](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1124>)
- Strong existing properties: shared table row renderer, explicit old-service labels, optional v2 details, HTML escaping of public values, client-facing reference formatting reuse, budget hiding for staff, confirmation before update/delete, and replacement of prior appointment subscription when starting dashboard. [Renderer](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:931>), [Labels](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1972>), [Details](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1053>), [Startup replacement](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:487>)

### Inferences
- **First fixes:** make one filter-aware render function run on view entry, realtime callbacks, successful mutations and rollback; keep the open modal synchronized or close it if the row is deleted; add loading/error/retry presentation and explicitly report caught failures. [Current refresh split](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:490>), [Filter function](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:969>)
- **Then reliability:** capture mutation IDs before awaits, disable pending controls, reject invalid transitions/unchanged values as needed, check affected rows, clean up listeners/cache on logout, and gate startup by role/focus. These are targeted improvements to the observed paths rather than a rewrite. [Mutation path](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:988>), [Delete path](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1124>), [Logout path](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:682>)
- **Then analytics/operations:** derive year dynamically or offer a date range; rename conversion as completion rate; use an explicit week/date scope; add reference/phone/service search and oldest-pending/follow-up views if staff need them. Introduce assigned operator, contact attempts, confirmed schedule, history and actual notification delivery only after the operational workflow is agreed, and use migrations for new fields. [Analytics formulas](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1512>), [Current search](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:969>), [Real-column rule](</C:/Users/John Aerol Tapales/Documents/Dacs Web/AGENTS.md:20>)

- The full `npm test` suite was not rerun by this researcher; no money or application code changed. The booking suite and isolated probes are the direct verification performed.
- This researcher did not inspect production `client_errors`; the user requested analysis rather than reporting a specific breakage. No automatic messaging was sent or configured.
