This is a public consultation **request intake** wizard plus an internal appointment register. It is not a reserved-slot scheduler or a client-portal appointment manager. The public form clearly describes its date and time as preferences; owner/staff follow-up is currently an operational task.

## Which problems have concrete evidence and how should they be prioritized?

### Takeaway
The strongest public-flow defect is mutable draft state during asynchronous save: the stored request and shown receipt can differ, or a stale response can complete a fresh wizard. Standard double-click protection exists; duplicate risk is instead in restart and ambiguous-response retries. Date and contact validation are intentionally lightweight and need a final consistency check.

### Cited Findings
- **P2 — Saved request and success receipt can disagree.** `submit()` snapshots a row synchronously before awaiting the insert, but `renderView()` later displays the current `S.bk`. `bkNext` is the only control disabled while saving; text inputs, Back, and routing remain active, and their handlers keep mutating state. An isolated execution of the unmodified extracted `submit()` function with a deferred in-memory insert showed persisted email `old@example.com` while confirmation state read `changed@example.com`. — [row snapshot and await](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:265>); [success reads live draft](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:192>); [only Next disabled](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:230>); [unguarded draft setter](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:259>); [input/Back listeners](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:309>).
- **P2 — Restart allows an old response to finish the new wizard.** Navigating to Services during an in-flight submit and clicking Book this service calls `start()`. It resets `saving: false`, replaces all answers and removes the completed flag; the old response then sets `done: true` on that replacement state with the old reference. The isolated extracted-function probe reproduced: stored service `interior-design`/stored name `Original`, shown service `architectural-design`/shown name empty, `done=true` with old ref. The same reset removes the guard against launching a second request while the first is pending. — [reset including saving=false](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:291>); [unguarded service reset](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/script.js:338>); [response commits global state](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:269>).
- **P2 — Retry is not idempotent after an ambiguous response.** Every invocation creates a new UUID. If a server commits the first insert but its response is lost, the generic “try again” path creates another pending row. An isolated mocked lost-response retry yielded two different UUIDs with identical contact/schedule data. This verifies client-side key regeneration, not that a real server committed a lost-response request. Conversely, two `submit()` calls on the same pending draft yielded **one insert**, proving the normal `S.saving` guard works. — [saving guard and fresh id](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:261>); [retry failure copy](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:138>).
- **P2 — Date can become invalid after it was selected.** `validateStep(3)` checks only that date/time are nonempty; `next()` validates only the current step, and final submit does not rerun calendar bounds. A visitor who chooses tomorrow then leaves the page until the next morning can submit a now-today date. An isolated helper probe showed `isBookable(2026-10-05, today=2026-10-05) === false` while `validateStep(3, {date:'2026-10-05',time:'10:30 AM',...}) === ''`. Calendar rendering prevents initial normal selection of prohibited dates; the finding is stale-state/final-validation weakness, not a claim Sundays are initially clickable. — [calendar rule](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:43>); [presence-only schedule validation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:75>); [current-step validation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:284>); [submit no revalidation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:261>).
- **P3 — Phone/contact acceptance is only a presence check.** Phone `x` passes step 4; the only format check is a permissive email regex. Inputs are not inside a form, have no required/maxLength/pattern constraints, and Continue is a type=button, so HTML native submit validation does not independently run. This matches the written simple validation spec; improving it is a product-quality choice, not a newly discovered violation of that spec. — [validator](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:79>); [contact markup](</C:/Users/John Aerol Tapales/Documents/Dacs Web/index.html:294>); [specified validation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/superpowers/specs/2026-10-01-index-v2-redesign-design.md:125>).
- **P3 — Reference is a short label, not a unique tracking token.** It exposes only 24 bits of the UUID (six hex characters). Distinct valid UUIDs `abcdef00-...` and `abcdef11-...` both produce `DACS-ABCDEF` in the live helper. UUID row IDs remain distinct; this is reference ambiguity if staff treat the displayed code as a unique lookup key. It is not evidence of actual observed collisions. — [reference helper](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:104>); [admin reference display](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1092>).

### Inferences
- Recommended first repair: capture an immutable submitted draft, guard pending reset/edit controls, and use a request-generation token so stale results cannot update a new wizard. Render the receipt from the submitted snapshot. Add a deferred insert test that edits/restarts while save is pending. — Basis: [submit](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:261>) and [start](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:291>).
- Recommended retry repair: hold the generated UUID across retries of the same draft, with a server-supported idempotent submission result. Do not fix this with public `.select()`, which conflicts with intended privacy access. Also do not indiscriminately `upsert()` from the anonymous browser; its update policy is a separate access decision. — Basis: [fresh UUID per attempt](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:265>) and [schema access constraint](</C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/DATABASE_SCHEMA.md:628>).
- Recommended validation repair: validate all four steps and `isBookable(parseDateKey(date), today)` immediately before submit, allow only offered enum values/time labels, establish timezone wording, and add tolerant phone sanity checking without excluding international callers. Reference enlargement or a distinct reference column needs DB/schema work if it becomes a persisted identifier. — Basis: [validators](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:65>), [available choices](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:15>) and [reference](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:104>).
- Do not treat lack of availability checks as a double-booking bug while this remains a preferred-schedule intake. If confirmed-slot scheduling is desired, capacity, duration, office/site/online travel constraints, holidays, rescheduling, cancellation and authoritative server validation need a separate design. — Basis: [preferred schedule copy](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:200>) and [static calendar](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:240>).

### Gaps
- UI races were reproduced using actual source-extracted async/reset functions and mocked deferred inserts, with rendering replaced by a no-op. This proves state/payload behavior, not an observed production incident or a screenshot of it.
- No real network timeout, committed duplicate, cryptographic collision, international visitor confusion, or screen-reader session was observed. Those are conditional risks supported by implementation evidence.
