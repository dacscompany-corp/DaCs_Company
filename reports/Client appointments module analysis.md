# Appointments capture requests but need safeguards

**DAC’s client appointments module is a consultation-request inbox with an internal status register.** Visitors describe their project and preferred schedule; owner/staff review the request and follow up manually. The public interface has useful validation, safe text rendering and sensible compatibility with older records, but several confirmed state and refresh defects can make the receipt or admin screen disagree with the database. The largest database concern is that the repository’s public insert policy does not enforce the wizard’s business rules; a separate deployment check must establish that migration 0084 actually removed the old broad read policy. Passing booking tests protect helpers and selected source patterns, but do not establish live permissions or reliable asynchronous behavior. This study, dated **2 October 2026, Asia/Manila**, inspected repository code, migrations, tests and isolated mocked probes; it changed no application code or production data. ## Visitors request a consultation; staff complete the handoff

The public entry is **`index.html` at `#/book`**, separate from the design-client, construction-client and partner portals. Header and other booking links enter the wizard; service/project calls to action reset it and preselect a service. Normal booking-route navigation preserves the in-memory draft, while the old `#appointment` route remains compatible. Targeted searches found no appointment-management implementation in the client or partner portals. ([Audience map](</C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:12>), [Wizard markup](</C:/Users/John Aerol Tapales/Documents/Dacs Web/index.html:239>), [Route compatibility](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/script.js:68>), [Service launch](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/script.js:338>))

The four steps collect meeting type/service, project/property/budget/location, preferred date/time, and name/email/phone. Visitors choose office, site or online consultation; five static time choices accompany a Monday–Saturday calendar running from tomorrow to three months ahead. Optional project details are text; attachments go through Messenger. **These choices express preferences, without checking capacity or reserving a slot.** The summary makes that scope visible. ([Choices and calendar rules](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:15>), [Step validation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:65>), [Attachment handoff](</C:/Users/John Aerol Tapales/Documents/Dacs Web/index.html:272>))

Submission generates a UUID, trims contact/free-text values and inserts a pending row directly into `appointments`. Database defaults supply creation/update timestamps. Success appears after the insert returns without an error and shows a short reference, submitted-request summary and Messenger link. Ordinary failure keeps the answers and reports the error through the shared reporter when available. **The insert deliberately does not read the record back:** the compatibility shim’s `.add()` performs a returning read, which conflicts with public insert-only permissions. ([Saved payload](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:86>), [Submission outcome](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/booking.js:261>), [Shim returning insert](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:371>))

The admin Appointments section groups Dashboard, Appointments, Analytics and Feedback. Owner and staff can use appointment views; worker/team-leader navigation excludes them. The table displays submission date, name, email, contact, service, preferred schedule, status and actions. Search covers name/email; filtering covers the four statuses. Details add reference, project context and optional message. Status changes write only status/update time; deletion permanently removes the row after confirmation. Transitions are unrestricted: completed can return to pending. No actor, reason or status history is stored by these paths. ([Navigation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:2264>), [Role filtering](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:2328>), [Table/filter](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:931>), [Status mutation](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:988>), [Delete](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1124>))

**Changing status to Confirmed sends no confirmation.** The receipt promises contact within 24 hours, but the checked repository has no appointment-specific email/SMS/push handler, reminder or delivery record. There is also no confirmed schedule, assigned operator, admin create/edit form, appointment print/export, public tracking/cancellation, or conversion into a client/project/invoice. Feedback is a separate testimonials surface grouped in the navigation. These are feature boundaries, not automatic defects: conflict prevention becomes necessary only if the product starts promising reserved meetings. External automations and actual manual follow-up were not inspected. ## One table connects public intake to the back office

The module uses plain HTML and vanilla JavaScript. Public writes use SQL column names directly; admin reads and mutations use the Firestore-compatible Supabase shim. `meeting_type` therefore appears as `meetingType` in admin, while `created_at` becomes a timestamp wrapper with `.toDate()`. Preferred dates remain ordinary date strings. **Appointments have no foreign key to profiles, clients, folders or construction projects**, and their estimated budget is a range label, not a contract value or accounting entry. With the repository migrations applied and suitable SQL grants, anyone can insert; only owner/staff can read, update or delete. Migration 0084 removes the historical policy allowing every signed-in account to read all appointments. **Live application of 0084 was not verified.** If absent, the old privacy exposure remains and the wizard’s new-column insert can fail. There is a separate, confirmed source-configuration gap: `appt_create` checks only `true`, and the table has no business constraints enforcing pending status, required contact, offered options, size limits or date window. Subject to actual grants, direct callers can insert non-pending requests or supply creation timestamps that distort metrics. **This is an integrity/abuse concern, not evidence of a live attack.** Tighten the public submission contract at the database or a controlled server entry point, while preserving intentional legacy compatibility and public read denial. No appointment-specific spam or rate-control mechanism was found in source. ([Permissive insert](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:299>), [Unconstrained base fields](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0001_init.sql:569>))

If enforcement must prevent staff API access as well as visible display, restrict the data/read surface; hiding more HTML alone would not provide that boundary. Module focus likewise narrows navigation without narrowing appointment RLS. ## Analytics measure submissions, not booked work or revenue

**Both monthly trend charts hardcode 2026.** Requests submitted in 2027 would still affect totals/status metrics but disappear from those charts. Replace fixed keys with a selected year or rolling date range. “Conversion rate” is completed appointments divided by all appointments; it does not measure won projects. “Weekly Activity” counts weekday submissions across all loaded history, not the current week or scheduled meetings. Popular Service shows only the first word, and the zero-record early return leaves previous metrics visible. Rename conversion to completion rate, state each date scope, show full service labels and reset empty metrics. ([Dashboard year](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1180>), [Analytics year](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1584>), [Metric formulas](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1512>), [Weekday histogram](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:1901>))

The active query requests all appointments in creation-date order without explicit paging; realtime reruns that full query after every table event. Growth will increase transfer/rendering work, and a configured API row cap can omit older history and understate analytics. Actual row count, cap and realtime publication were not checked. Add explicit paging/date filters and compute totals from a complete, defined dataset. The separate 200-row loader is not the active subscription path. ([Active query](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:488>), [Alternate loader](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/admin.js:817>), [Full refetch](</C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:357>))

Several foundations are worth preserving: public/admin text escaping, shared schedule/reference helpers, old-service labels, optional-field handling, explicit staff budget hiding, native disabled calendar buttons, and focus restoration after rendered controls change. Local date parts correctly avoid the PH UTC rollback hazard. Remaining P3 refinements include reasonable contact/length checks, timezone wording for overseas online callers, field-specific accessible errors, and a more durable receipt. Current drafts/receipts disappear on refresh; the short reference is a support label rather than a tracking credential. ## Verification should prove delivery and permissions before expanding scope

The research runs recorded **24 booking tests passed, zero failed**, and a syntax check of `js/booking.js` passed. The suite checks date/calendar/validation helpers, payload/reference, route compatibility, migration text, service labels, the staff budget gate, script order and the no-read-back save pattern. These tests do not apply migrations or simulate the asynchronous races above. Existing database role checks contain no appointment allow/deny cases. ([Booking checks](</C:/Users/John Aerol Tapales/Documents/Dacs Web/tests/booking.test.js:1>), [Migration/source tests](</C:/Users/John Aerol Tapales/Documents/Dacs Web/tests/booking.test.js:131>), [Existing DB checks](</C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/tests/rls_checks.sql:1>))

The most useful next verification is a staging role matrix covering anonymous, client, partner, worker, staff and owner reads/writes; it should also try non-pending, incomplete and oversized public inserts. Confirm live columns/policies/grants, then exercise public submission without returning reads, two admin sessions with active filters, failed saves, close-during-delete, midnight rollover and ambiguous retries. Add focused deferred-save and snapshot tests around the actual state transitions. No production login, booking, realtime delivery, mobile/screen-reader session or external automation was tested in this study; passing source checks cannot substitute for those observations.

Repair the intake/state/refresh paths first, then align the 24-hour promise with a named person and a follow-up procedure. If DAC’s needs booked meetings, design confirmed date/time, capacity, duration, holidays, assignment, rescheduling/cancellation and communication delivery as a separate capability. New persisted fields require real columns, a correctly numbered migration and schema documentation; every public save/receipt/admin render/test path in the file map needs review. The analysis supports focused repairs without a rewrite, while keeping consultation preferences separate from project and money records.
