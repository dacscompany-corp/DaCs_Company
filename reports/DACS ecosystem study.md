# DACS connects operations through shared backend

Study date: 28 September 2026. Scope: Dacs Web, Dacs Attendance, and dacs_construction_mobile.

**DACS has two active software systems sharing one operational backend, plus an unused Flutter prototype.** Web owns administration, business records, financial reporting, and the Supabase backend; the native Attendance app provides worker capture and offline submission. The user confirmed that the Flutter construction app is an older prototype and is not in use. The active systems show substantial attention to financial correctness and field reliability, but their highest-value next improvements concern server authorization, reliable compound saves, and offline identity handling. Web's existing local tests passed; Attendance's fresh test run was blocked by the local execution environment; the prototype's sole test failed. Findings in this report describe inspected source and local checks, **not confirmed production incidents or a live security audit**. The study traced principal architecture, data contracts, money rules, authentication, offline capture, external services and release boundaries; it does not claim every line or every workflow was reviewed.

## Two active applications share authority across repositories

The most useful ecosystem map is based on data ownership rather than folder names. Web is plain HTML and global JavaScript, with React used on Project Control, and no application build step. Its Firestore-looking calls are a compatibility layer over Supabase Postgres, Auth, Storage and Realtime. Consequently, changing the database remains a real schema change: adding an ordinary JavaScript property without its mapped column can break saving. Attendance's Kotlin app calls this shared backend directly, while the Flutter prototype still calls actual Firebase. ## Financial isolation and durable capture preserve business meaning

DACS's financial rules are intentional business contracts. **Labor includes direct work and its statutory burden; indirect work and its burden belong to Overhead exactly once.** Spent is Labor plus Material plus Overhead. Earned follows BOQ accomplishment multiplied by contract value; a contract-based fallback is a forecast. Cover money remains inside ordinary spending, with Cover reported as a subset rather than a fourth bucket. Client allocation is a funding/planning quantity, not earned revenue or a substitute for actual spending. These distinctions are implemented in live functions and guarded by regression tests. ([Cost calculation](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/portal-app.compiled.js:403>), [Spent](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/portal-app.compiled.js:316>), [Earned and recognition](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/portal-app.compiled.js:348>), [Money contract](<C:/Users/John Aerol Tapales/Documents/Dacs Web/docs/ARCHITECTURE.md:149>))

Reimbursements, quotations, warranty reserves/draws and Attendance reporting are deliberately outside that ledger. A proposal is not revenue, an owner's reimbursement tracker is not another project expense feed, and internal warranty reserves are not client billing deductions. **Attendance hours do not determine pakyaw pay.** Weekly attendance rewards now include a peso amount, but marking a reward handed over records a reported state; it does not create payroll, payment or accounting entries. Future integration must preserve these distinctions unless the owner deliberately changes the business model. ([Isolation tests](<C:/Users/John Aerol Tapales/Documents/Dacs Web/tests/money-math.test.js:1>), [Attendance module contract](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:11>), [Reward state](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:4102>))

Attendance provides a more developed offline design than either Web or the Flutter prototype. A worker passes login and versioned terms, selects a project, captures and reviews a photo, writes a description and confirms. A UUID remains stable across retries. The submission enters Room before network delivery; pending data includes worker/project identity, capture and trusted times, location evidence and offline state. Successful server acknowledgement updates the local record, removes the queue row and deletes the local photo; permanent failures remain available rather than silently disappearing. ([Navigation](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/ui/AttendanceRoot.kt:79>), [Capture flow](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/ui/timeflow/TimeFlowViewModel.kt:29>), [Durable submission](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:76>), [Queue outcome handling](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionWorker.kt:180>))

Authentication uses the shared attendance-signin function to check worker/teamLeader eligibility and throttling. Server RPCs validate active status, owner/project access, Manila work date and idempotency. The app resizes and stamps private photos, uploads them before the RPC, and displays stored evidence through expiring signed URLs. Room migrations are explicit through schema version 5, without destructive fallback. These are meaningful safeguards worth preserving during any refactor. ([Sign-in](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/attendance-signin/index.ts:49>), [RPC validation](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0078_attendance_trusted_time.sql:171>), [Photo handling](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/local/PhotoStore.kt:25>), [Signed URLs](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/AttendancePhotos.kt:12>), [Room migrations](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/di/DatabaseModule.kt:28>))

The evidence rules have limits that affect worker disputes. Denied/disabled location, mock fixes and accurate out-of-fence fixes are refused; unavailable or insufficiently accurate fixes can remain recordable, with verification implications. Trusted time uses a server-date anchor plus elapsed device time and boot count, not a claim of protection against a modified APK. Location is fetched at submission after photo review and description, not at the shutter instant. The difference matters if the product promises that the image and location prove the same instant. ([Location policy](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/domain/LocationVerification.kt:178>), [Clock anchor](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/local/ClockAnchorStore.kt:39>), [Security limit](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0078_attendance_trusted_time.sql:58>), [Capture and later location](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/ui/timeflow/TimeFlowViewModel.kt:138>))

## Server authority and save reliability deserve attention first

The priorities below separate demonstrable source behavior from consequences that still require controlled reproduction. **No production exploit, data loss or worker incident was demonstrated.** Priority reflects the potential impact if deployed behavior matches the reviewed files.

| Priority | Source finding | Why it matters and next verification |
|---|---|---|
| High | Account creation trusts caller-supplied ownerUid | Establish server-derived tenant identity and an explicit role-grant policy; verify with separate owner/staff tenants |
| High | Push subscription and delivery lack project/recipient authorization checks | Prevent cross-project financial notifications and staff peso payloads; test writes and delivery separately |
| High | Compound financial saves are sequential rather than transactional | Verify invoice parent/line failure handling and move critical saves behind transactional operations |
| High-confidence field reliability issue | Offline project lookup uses a different identity fallback from restored attendance sessions | Reproduce cached-session refresh failure and unify worker identity resolution |
| High — confirmed policy gap | Staff amounts are hidden in screens but remain retrievable through permitted API rows | User confirmed backend confidentiality is required; enforce restricted server reads and staff-safe notifications |
| Medium | AI worker lacks application request authentication/rate limiting; new-user provisioning lacks compensation | Bound AI access and test partial account-creation failure/retry |
| Medium | Attendance drains and empty-project cache behavior need coordination | Test overlapping workers and cache invalidation on real devices |

**Account creation has a concrete tenant-authority gap.** The endpoint validates the caller and accepts owner/staff, blocks staff from creating owners, but writes the caller's requested ownerUid through service-role access without deriving or checking it against the caller's tenant. A newly created staff profile under that chosen owner would resolve data access through the corresponding owner_id policies. The normal UI supplying the correct value does not constrain a direct endpoint caller. This is stronger evidence than a missing browser check, but deployed function and policy versions were not inspected. ([Caller validation](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:45>), [Role restriction](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:68>), [Profile assignment](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/functions/admin-create-user/index.ts:97>), [Tenant access helpers](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:21>))

Push has a related boundary problem. Subscription project_id is unconstrained text, self policies check row ownership without project permission, and the scheduler uses privileged reads to send financial summaries without rechecking current tenant, project access or staff status. The ordinary admin bell has no staff guard. Therefore the current staff presentation protections do not extend consistently to notifications. Fixing only subscription UI would leave direct writes and stale subscriptions unresolved; delivery needs current recipient authorization too. ([Subscription policy](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0011_push_subscriptions.sql:5>), [Self policy](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0012_push_partner.sql:11>), [Bell](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/push-notify.js:178>), [Scheduler](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:37>), [Financial payload](<C:/Users/John Aerol Tapales/Documents/Dacs Web/cloudflare-worker-notify/worker.js:113>))

The facade creates another important mismatch between familiar API names and actual guarantees. Its batch commit awaits writes individually without rollback. Nested invoice replacement updates the parent, deletes child rows, and inserts replacements; the deletion result is ignored. An insertion failure after deletion can leave missing lines, and a failed deletion followed by a successful insertion can produce unwanted duplicates. These are identifiable failure paths, not observed production losses. Correct arithmetic tests cannot establish atomic persistence. ([Parent/child write](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:423>), [Child replacement](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:478>), [Batch commit](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/supabase-config.js:518>))

Attendance's strongest immediate reliability finding is an **inconsistent offline worker identity**. Session restoration and attendance submission can use cached worker identity during refresh failure, while the project repository can derive an empty ID from currentUserOrNull. That lookup misses the worker's existing cached projects in the very offline state the root allows. Separately, immediate and periodic work use different unique names and both drain submissions; no shared claim or mutex was found. Record idempotency mitigates duplicate server attendance, but does not itself serialize photo uploads. A successful empty project response also leaves old cache rows intact, allowing retired choices to reappear during later network failure; server checks still reject invalid submissions. These findings need device reproduction before assigning incident frequency. ([Session fallback](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/SupabaseAuthRepository.kt:162>), [Project lookup/cache](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/data/repo/OfflineAttendanceRepository.kt:274>), [Work names](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionScheduler.kt:17>), [Drain](<C:/Users/John Aerol Tapales/Documents/Dacs Attendance/app/src/main/java/com/dacs/attendance/work/SubmissionWorker.kt:102>))

**Staff reward amounts are currently hidden in Web UI and CSV access; the architecture document saying otherwise is stale.** However, the reward query still selects amount and scoped staff RLS permits the underlying rows. Payroll and expenses similarly allow full-row staff access through the shim. The user explicitly confirmed during this study that staff must be blocked from peso amounts in both the interface and backend. Therefore the reviewed API/RLS access is a confirmed source-level policy gap, not an unresolved presentation preference. Remediation requires backend enforcement, not additional CSS or formatting; live deployment parity still needs verification. Profile policies also merit a tenant-boundary review because source grants are broader than the ordinary UI routes suggest. ([Current reward guard](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:4112>), [Query](<C:/Users/John Aerol Tapales/Documents/Dacs Web/js/attendance-admin.js:4054>), [Reward RLS](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0066_attendance_weekly_reward.sql:119>), [Cost policies](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0002_rls.sql:117>), [Profile update policy](<C:/Users/John Aerol Tapales/Documents/Dacs Web/supabase/migrations/0019_admin_profile_updates.sql:39>))

## Stabilization needs explicit ownership and a few decisions

The recommended next phase is a controlled stabilization effort, not a broad framework rewrite. First, compare deployed functions, policies, migrations and worker versions against the source using read-only inspection, then reproduce account-tenant and notification authorization cases in an isolated environment. The confirmed staff confidentiality requirement should be enforced across database/API responses and notification delivery, with tests proving that staff cannot retrieve amounts directly while permitted nonfinancial workflows still work. In parallel, reproduce the offline identity failure on representative worker phones. Next, make financial parent/child writes transactional and exercise failure between steps; preserve all current arithmetic and isolation tests. Then test overlapping submission workers, empty-project cache replacement, refresh failure, offline reboot, shared-phone logout and eventual sync. Finally, update architecture and release documentation from verified behavior, including the migration-before-APK sequence and ownership of Vercel, Supabase and Cloudflare changes. These priorities follow the demonstrated authority, persistence and offline contracts rather than adding unrelated features.

The highest-value follow-up decisions are below. They are deliberately narrow because changing them changes the correct technical solution.

| Decision needing clarification | Why the answer matters |
|---|---|
| Is this permanently one trusted company, or must different owners be isolated? Which roles may staff create? | Determines tenant policy boundaries and the provisioning authority matrix |
| Who owns APK distribution, minimum-version rollout and backend release verification? Which versions remain on worker phones? | Determines a safe migration/upgrade/rollback plan |
| Must attendance location correspond to shutter time, and who resolves legitimate unverified days, missed Time Out and bonus disputes? | Determines capture timing, evidence language and the admin exception workflow |
| Should the Flutter prototype be retained as an archived reference, retired with historical data preserved, or used as a design reference for procurement in an active surface? | Prevents maintaining a third backend/client without a product purpose |

No application code, deployment or live data was changed for this study. ## Conclusion

DACS's most valuable existing design choice is explicit business separation: different project identities, labor versus overhead, spent versus funded, and attendance evidence versus pay. Its next improvement should make those boundaries equally explicit in server permissions, transaction boundaries and release procedures. That preserves the working business model while reducing the classes of failure that local arithmetic tests cannot detect.
